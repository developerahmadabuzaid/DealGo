# DealGo — Security and Reliability Audit

Date: 30 September 2026
Scope: `src/` (.NET 10 API, EF Core, PostgreSQL, Redis, SignalR), `mobile/` (Flutter), `wwwroot/admin` (console)
Method: read-only review of the code. **No file was changed.**

---

## Executive Summary

| Level | Count |
|---|---|
| CRITICAL | 2 |
| HIGH | 4 |
| MEDIUM | 9 |
| LOW / INFO | 7 |

**The honest headline: the hard parts are done well.** Money and bidding are correct. Every path that
moves money takes a real row lock (`SELECT ... FOR UPDATE`) inside a database transaction, every
repeatable action carries an idempotency key, prices and times come only from the server, raw SQL is
parameterised everywhere, refresh tokens are stored as hashes and reuse revokes the family, and the
error contract already returns a machine-readable `code`. I found **no** price manipulation, **no**
double-spend, **no** way to bid as another user, and **no** SQL injection.

The problems are elsewhere: a few endpoints hand out data they should not, the live site cannot
actually send a login code, and a handful of expected failures still arrive as `500`.

**Top reliability problem:** no one can sign in to the live site, because no OTP provider is
configured and the sender only writes to the log (C-1).

**Top security problem:** any logged-in user can read the name and email address of every
participant in every auction (C-2).

### C-1 — Production cannot send a one-time code

* **Location:** `src/AuctionPlatform.Infrastructure/DependencyInjection.cs:135`,
  `src/AuctionPlatform.Infrastructure/Services/OtpSender.cs`
* **Vulnerability class:** availability / broken authentication (OWASP API2)
* **Why it happens:** `IOtpSender` is always `LoggingOtpSender`. Outside Production it writes the code
  to the log; in Production it writes an error and delivers nothing. There is no Twilio / SNS /
  SendGrid client anywhere in the solution.
* **Attack / failure scenario:** a real customer opens the live app, types a Saudi mobile number, and
  waits for a code that is never sent. The API answers `200` with a normal-looking challenge, so
  nothing on screen says anything is wrong. The same applies to withdrawals, because
  `Auction:RequireOtpForWithdrawal` is `true`.
* **Business impact:** the live platform has no working sign-up or sign-in for phone users, and no
  withdrawals at all. For a client demo this is the first thing that will be tried.
* **Recommended fix (backend):** implement `IOtpSender` against a Saudi-capable SMS gateway (Unifonic,
  Taqnyat, or AWS SNS) plus an email sender, register it when the provider settings are present, and
  **refuse to start in Production** when they are not — the same pattern already used for `Jwt:Secret`.
  Until then, treat the live site as demo-only with a seeded account.
* **Flutter fix:** none needed; the client already shows `OTP_*` codes properly.
* **Test required:** an integration test asserting that a Production-like host with no provider
  configured fails startup, and a unit test that the sender is called with the right destination.

### C-2 — Any logged-in user can read every participant's name and email

* **Location:** `src/AuctionPlatform.Api/Controllers/AuctionsController.cs:58`
  → `src/AuctionPlatform.Application/Auctions/AuctionService.cs:252`
* **Vulnerability class:** Broken Object Level Authorization + excessive data exposure
  (OWASP API1 + API3)
* **Why it happens:** the endpoint carries a bare `[Authorize]`. The admin copy of the same list
  (`AdminAuctionsController:106`) correctly requires `Permissions.AuctionRead`; this one requires
  nothing but a token. The projection returns `p.User.FullName` and `p.User.Email`, and `PagedQuery`
  allows `pageSize=200` plus a free-text `search`.
* **Attack scenario:** sign up with any phone number (sign-up on login is open), list auctions from
  the public endpoint, then call
  `GET /api/v1/auctions/{id}/participants?pageSize=200&page=1` for each auction. With 400 required
  participants per auction, that is the full customer list — names and email addresses — in a few
  dozen requests. The `search` parameter even lets an attacker confirm whether a specific person is
  a customer.
* **Business impact:** a personal-data breach. Under Saudi PDPL this is reportable. It also hands a
  competitor your customer list and gives a phisher a target list that is known to hold wallet
  balances.
* **Recommended fix (backend):** decide what a participant may legitimately see, and serve only that.
  The masked, ranked `GET /auctions/{id}/leaderboard` already exists and already exposes nothing
  private. Either delete this endpoint from the public controller, or restrict it to
  `Permissions.AuctionRead` and let the app keep using the leaderboard.
* **Flutter fix:** check nothing in the app calls it. (It does not — `auction_repository.dart` uses
  `/leaderboard`.) So this endpoint can be removed with no client change.
* **Test required:** an integration test that an ordinary user's token gets `403` from
  `/auctions/{id}/participants`, and that the leaderboard still returns masked names.

## Authorization Findings

### H-1 — A shipping address id is never checked against its owner

* **Location:** `src/AuctionPlatform.Application/Store/StoreOrderService.cs:180`;
  `src/AuctionPlatform.Application/Prizes/PrizeClaimService.cs:209` and `:240`
* **Vulnerability class:** IDOR / BOLA (OWASP API1)
* **Why it happens:** `request.ShippingAddressId` is copied straight onto the order or claim. Nothing
  compares it to `ShippingAddresses.UserId`. Reading it back is then legitimate, because
  `GetOrderAsync` filters on `o.UserId == userId` and happily `Include`s the attached address.
* **Attack scenario:** an attacker who learns an address id — from a shared screenshot, a log, an old
  response, or an insider — puts it in their own checkout body. `GET /store/orders/{id}` then returns
  that person's full name, phone number and street address inside the attacker's own order.
* **Mitigating factor:** address ids are GUIDs, so they cannot be guessed. This is why it is HIGH and
  not CRITICAL. It is still a broken access control.
* **Second problem, same line — a reliability bug:** a *wrong* GUID violates the foreign key.
  `DbUpdateException` with SQL state `23503` is not the unique-violation case the middleware handles,
  so the customer gets `500 INTERNAL_ERROR` on a perfectly ordinary mistake.
* **Recommended fix (backend):** inside the checkout transaction, load the address by
  `(Id == request.ShippingAddressId && UserId == userId)` and throw
  `DomainException(ErrorCodes.NotFound, "Address not found.")` when it is missing. Same in both prize
  methods.
* **Flutter fix:** none; the app only sends ids it received from `GET /store/addresses`.
* **Test required:** user B checks out with user A's address id → `404`; and with a random GUID →
  `404`, not `500`.

## API Security Findings

### H-2 — Admin tokens in `localStorage`, and no Content-Security-Policy

* **Location:** `src/AuctionPlatform.Api/wwwroot/admin/app.js:44-52`;
  header block in `src/AuctionPlatform.Api/Program.cs`
* **Why it matters:** the console stores both the access token **and the refresh token** in
  `localStorage`, and `Jwt:RefreshTokenDays` is `0`, which means refresh tokens never expire by time.
  Any script that runs on the console's origin can read both and hold administrator access forever.
  `X-Content-Type-Options`, `X-Frame-Options` and `Referrer-Policy` are set, but there is **no CSP**,
  which is the one header that would stop injected script from running or from sending the token out.
* **What is already right:** uploads are validated by magic bytes, not by file name or `Content-Type`
  (`AdminUploadsController`), so the obvious stored-XSS route — upload HTML as `.jpg` on our own
  origin — is closed. That is good work and it is why this is HIGH and not CRITICAL.
* **Recommended fix:** add a strict CSP to the console's responses
  (`default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'none';
  frame-ancestors 'none'`) and move the refresh token to an `HttpOnly; Secure; SameSite=Strict`
  cookie so script cannot read it. Keep the short-lived access token in memory only.
* **Test required:** a test asserting the CSP header is present on `/admin/index.html`.

### H-3 — Swagger is public in Production

* **Location:** `src/AuctionPlatform.Api/Program.cs` — `app.UseSwagger()` and `app.UseSwaggerUI()`
  run unconditionally.
* **Why it matters:** `https://dealgosa.com/swagger` publishes every route, every request shape and
  every admin endpoint to anyone. It is not a vulnerability by itself, but it removes all the work an
  attacker would otherwise have to do, and it advertises endpoints such as C-2 above.
* **Recommended fix:** wrap both calls in `if (!app.Environment.IsProduction())`, or put them behind
  the `AdminArea` policy.

### M-1 — The bid rate limiter fails open when Redis is away

* **Location:** `src/AuctionPlatform.Infrastructure/Services/RedisServices.cs:105`
* **Why it happens:** `RedisRateLimiterService.TryAcquireAsync` catches everything and `return true`.
  That is deliberate and documented for the distributed **lock** (where PostgreSQL still guarantees
  correctness), but for the rate **limiter** it means the per-user bid ceiling — 5 per second, 120 per
  minute — simply disappears.
* **What remains:** the in-process `"bidding"` token bucket in `Program.cs` (10 tokens, 5/s). That is
  per instance, so with two instances the real ceiling doubles.
* **Business impact:** during a Redis blip a scripted client can bid far faster than a human, which in
  a rank-by-highest-price auction is a direct unfairness, not just load.
* **Recommended fix:** keep failing open for the lock; fail **closed** for the bid limiter, or fall
  back to the in-memory limiter instead of allowing everything. Log it at `Error`, not `Warning`.
* **Test required:** a unit test with a broken multiplexer asserting the limiter refuses.

### M-2 — SignalR hub methods are not rate limited

* **Location:** `src/AuctionPlatform.Api/Hubs/AuctionHub.cs`
* **Why it happens:** `app.UseRateLimiter()` is HTTP middleware. Once the WebSocket handshake is done,
  hub invocations do not pass through it. `JoinAuction` and `GetSnapshot` each run a database query.
* **Attack scenario:** one authenticated client calls `GetSnapshot` in a tight loop over an open
  socket and generates unbounded database load with no throttle anywhere.
* **Recommended fix:** a per-connection counter in the hub (the existing `IRateLimiterService` keyed
  on `Context.ConnectionId`), refusing after a few calls per second.

### M-7 — CORS and `AllowedHosts` are wider than needed

* **Location:** `Program.cs` CORS policy; `appsettings.json` `"AllowedHosts": "*"`
* The policy uses a proper origin allowlist (good), but adds `AllowAnyHeader`, `AllowAnyMethod` and
  `AllowCredentials`. It exists for the console and the PWA, which are served from the API's **own**
  origin and therefore need no CORS at all — only the Flutter web build at another origin does.
* A pure mobile client never needs CORS; browsers enforce it, native apps ignore it.
* **Recommended fix:** set `Cors:AllowedOrigins` to exactly `https://dealgosa.com` in production, list
  the methods and headers actually used, and set `AllowedHosts` to the real host names.

## Reliability Findings

### M-4 — There is no request validation layer

* **Evidence:** `FluentValidation.DependencyInjectionExtensions` is referenced in
  `AuctionPlatform.Application.csproj`, but the solution contains **zero** `AbstractValidator`
  classes, and no `[Required]`, `[MaxLength]` or `[Range]` attribute on any request record.
* **Consequence:** the database column length is the only limit. A `FullName` longer than its column
  makes PostgreSQL raise `22001 value too long`, which is a `DbUpdateException` that is neither a
  unique violation nor a connection failure — so it falls to the last arm of the middleware and the
  user gets `500 INTERNAL_ERROR` instead of `400 VALIDATION_FAILED`.
* **This is the direct answer to your Part 2 question.** The contract itself is right; what breaks it
  is that a whole class of ordinary bad input never becomes a `DomainException` at all.
* **Recommended fix:** add validators for the request records that carry free text and numbers
  (register, update profile, address, checkout, admin auction create). Separately, add a
  `DbUpdateException` arm to the middleware mapping SQL states `22001` (too long), `23503` (foreign
  key) and `23514` (check constraint) to `400 VALIDATION_FAILED` — a small change that closes the
  whole family at once.

### M-5 — 22 error codes have no Arabic wording

* **Location:** `mobile/lib/core/localization/app_strings.dart:369` (`_errorsAr`)
* Missing, among others: `SERVICE_UNAVAILABLE`, `PRODUCT_NOT_FOUND`, `ORDER_NOT_FOUND`,
  `PAYMENT_METHOD_NOT_ACCEPTED`, `STORE_DISABLED`, `ORDER_AMOUNT_OUT_OF_RANGE`, `INVALID_AMOUNT`,
  `WALLET_NOT_FOUND`, `CURRENCY_MISMATCH`, `PRIZE_CLAIM_NOT_PAYABLE`, `PRIZE_CLAIM_NOT_CLAIMABLE`,
  `NOT_FOUND`, `CONFLICT`, `INVALID_REFRESH_TOKEN`, `INVALID_AUCTION_STATE`, `DUPLICATE_SKU`,
  `REQUEST_CANCELLED`.
* `displayMessage` falls back to `message`, which is the server's **English** sentence. So an Arabic
  user whose database is briefly down reads *"The service is temporarily unavailable."*
* **Recommended fix:** add the missing entries. Also add a test that walks the backend `ErrorCodes`
  list and fails when a code has no Arabic text — that stops the gap coming back.

### M-6 — No global error handler in the Flutter app

* **Location:** `mobile/lib/main.dart:21`
* `main()` calls `runApp` directly. There is no `FlutterError.onError`, no
  `PlatformDispatcher.instance.onError`, no `runZonedGuarded`, and no crash reporter.
* **Consequence:** an unexpected exception inside a widget gives a grey screen in release and nothing
  reaches you. This is exactly the "the app stops and says nothing" case in your brief.
* **Recommended fix:** wrap `runApp` in `runZonedGuarded`, set both handlers, show a friendly
  "something went wrong — try again" screen through `ErrorWidget.builder`, and send the stack
  somewhere you can read it.

### M-9 — Two silent catches on the client can hide a real failure

* `mobile/lib/features/auctions/data/auction_repository.dart:62` — `myParticipation` turns **any**
  error, including a timeout or a `500`, into `null`, which the UI reads as "you have not joined".
  A participant who has already paid the entry fee can be shown the Join button again.
* `live_auction_controller.dart:165` — `_loadDetail` swallows its failure. Defensible (the snapshot
  carries what the screen needs) but worth logging.
* **Recommended fix:** in `myParticipation`, return `null` only for a genuine `404` /
  `PARTICIPANT_NOT_FOUND` and let everything else propagate.

### M-3 — `Include Error Detail=true` in the base settings

* **Location:** `src/AuctionPlatform.Api/appsettings.json` connection string
* This tells Npgsql to put **parameter values** into exception messages. Clients never see them (the
  middleware returns a generic message outside Development), but Serilog writes them to the console
  and to `logs/api-*.log`. Those parameters include phone numbers, email addresses and amounts.
* **Recommended fix:** keep it only in `appsettings.Development.json`.

### M-8 — Uploaded pictures still default to the container disk

* `appsettings.json` has `Storage:Provider = "Local"`. Production depends entirely on the
  `Storage__Provider` environment variable being set on the container app. One missed variable on a
  future revision and every uploaded picture is thrown away with the container — which is what
  already happened once.
* Still outstanding from before: the container app identity
  `7f93d064-d3f7-4b50-b395-e54cfd59ca3c` needs **Storage Blob Data Contributor** on
  `dealgomedia2026`, or uploads keep failing with `403`.
* **Recommended fix:** make the API refuse to start in Production when `Storage:Provider` is `Local`,
  the same way it refuses a missing JWT secret.

## Auction, Balance and Concurrency Findings

This is the part I expected to find problems in, and did not. Recording it plainly, with evidence:

| Question from your brief | Answer | Evidence |
|---|---|---|
| Can you bid after the auction ends? | No | `BidService.cs:172` re-reads `EndsAt` **under the row lock** against the server clock |
| Can the client send a price? | No | The bid body is only `{ idempotencyKey }` — `AuctionsController.cs:83` |
| Can the increment be skipped? | No | `AuctionRules.NextPrice` derives the price from the locked row |
| Can you bid as someone else? | No | The user id comes only from the validated token — `ApiControllerBase.cs:16` |
| Can a device clock be used? | No | Every timestamp is `IDateTimeProvider.UtcNow`; the app derives its countdown from `snapshot.serverTime` |
| Double-spend / TOCTOU on balance? | No | `WalletService.MoveAsync` locks the wallet row with `FOR UPDATE`, then checks and writes inside the same transaction |
| Two buyers, last unit in stock? | No | `StoreOrderService` locks every product row in id order, then re-reads stock under the lock |
| Replayed bid or checkout? | No | Idempotency key plus a unique index; the fast path returns the original result |
| Two instances starting one auction? | No | Distributed lock **and** a conditional `ExecuteUpdateAsync` that matches only while unstarted |
| Two instances declaring winners? | No | `FOR UPDATE` on the auction plus the `WinnersDeclared` flag; refunds guarded by `UNIQUE(AuctionId, ParticipantId)` |
| Deadlock between paths? | Not found | Lock order is consistent: auction → wallet, products (id order) → wallet. No path takes them in reverse |
| SQL injection? | No | All 12 `FromSqlRaw` sites use `{0}` parameters; no string interpolation anywhere |

The residual concurrency risks are **M-1** (limiter fails open) and **M-2** (hub flooding). Both are
fairness and load problems, not correctness problems.

## Authentication Findings

Reviewed and correct:

* Signature, issuer, audience, lifetime and signing key are **all** validated, with a 30-second
  clock skew (`Program.cs`). HMAC-SHA256 only — no algorithm confusion.
* Production refuses to start without a 32-character `Jwt:Secret`.
* Refresh tokens: 64 random bytes, stored only as SHA-256, single-use, and replaying a consumed one
  revokes the whole family for that user. This is better than most codebases.
* Login returns the same error for an unknown email and a wrong password. The OTP request endpoint
  returns a **decoy challenge** for unknown destinations, so it cannot be used to discover accounts.
  That is a thoughtful detail.
* The token in the SignalR query string is accepted **only** for the hub path.
* Tokens in the app live in `flutter_secure_storage` (Keychain / EncryptedSharedPreferences), never in
  plain preferences.
* Withdrawal codes are bound to a SHA-256 fingerprint of amount + currency + destination, so a code
  for a small transfer cannot approve a large one.
* One `debugPrint` in the whole app, in `arena_sounds.dart`, and it prints no user data.

Open: **L-1** — `Jwt:RefreshTokenDays = 0` means a session never expires by time. That is a deliberate
product decision, but it means a stolen refresh token is valid until the user signs out. Consider a
long hard maximum (90 days) so there is an upper bound.

## Observability Findings

Present and working: Serilog to console and rolling file (14 days), OpenTelemetry tracing and
metrics, `SerilogRequestLogging`, health checks split into `/health`, `/health/live` and
`/health/ready`, an `AuditService`, and the process-lifetime hooks added earlier that log a crash, an
unobserved task failure, and a normal shutdown.

Gaps:

* **No correlation id is returned to the client.** The error envelope is `{ code, message, details }`
  with no `traceId`, so a user reporting "it failed" cannot be matched to a log line. Adding
  `traceId` (from `Activity.Current?.Id ?? HttpContext.TraceIdentifier`) is a small, additive change
  and is the single most useful improvement to support.
* No alerting on `LogCritical` / `LogError`. The lifetime hooks write a good message; nothing reads it.
* `/health` is anonymous and names its components (`postgres`, `redis`) with status. Minor, but it
  tells an attacker your stack.

## Recommended Error Contract

My recommendation is **do not redesign it.** The existing envelope is already stable,
machine-readable, versionable and easy to consume, and the app already branches on `code` and never
on text. Changing its shape would break every screen for no gain.

Two additive changes only — both backward compatible, because the app reads fields by name:

```jsonc
{
  "code": "INSUFFICIENT_BALANCE",   // unchanged — the contract
  "message": "Insufficient balance for this operation.",
  "details": [],
  "traceId": "00-4bf92f…-01"        // NEW: so a report can be found in the log
}
```

And one mapping change in `ExceptionHandlingMiddleware.Map`, so ordinary bad data stops being a `500`:

```csharp
DbUpdateException db when SqlState(db) is "22001" or "23503" or "23514"
    => (400, ApiError.Create(ErrorCodes.ValidationFailed, "Some of the submitted data is not valid.")),
```

`success: false` is not worth adding: the HTTP status already carries it, and the app would have to
learn a second way to ask the same question.

## HTTP Status Code Review

`StatusForCode` in the middleware is correct and complete for the codes it lists. The default arm —
"a well-formed request the rules decline is a 400" — is a sound choice.

Three cases where the status is wrong today:

| Case | Today | Should be | Why |
|---|---|---|---|
| String longer than its column | `500 INTERNAL_ERROR` | `400 VALIDATION_FAILED` | M-4 |
| Foreign key violation (bad address id) | `500 INTERNAL_ERROR` | `404` or `400` | H-1 |
| `ENTRY_PAYMENT_REQUIRED` | `400` | `402` or `409` | It is a state conflict, not bad input. Cosmetic |

`422` is never used. That is fine — `400` with `VALIDATION_FAILED` plus `details` carries the same
information, and one convention is better than two.
