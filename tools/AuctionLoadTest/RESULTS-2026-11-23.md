# Bidding load test — results, 23 November 2026

**Build tested:** the one live on dealgosa.com since 23 Nov (git tag `perf-baseline-2026-11-23`,
commit d46ef67), plus read-only measurement: the admin diagnostics endpoint and timers around the
bid and join locks. The bidding logic itself is unchanged.

**Where:** this machine (32 cores), API in Release with Redis off as on SmarterASP, PostgreSQL 16 in
Docker. Two database settings: on the same machine (0 ms), and with 1 ms added each way (2 ms per
round trip) to stand in for SmarterASP's separate database server.

**How people bid:** like someone with the app open — at random moments, about 0.5 bids a second
each, 2 a second in the last 15 seconds; one bid in flight at a time; never straight after their
own bid. Paid auctions (20 SAR entry), 90 seconds, closing by time. For scale: the auction in the
video had 13 people placing about 5 bids a second in total.

Full reports: `artifacts/loadtest/2026-11-23-main`, `-db1ms`, `-target` (report.md, results.json,
every bid in attempts-N.csv).

## Accuracy held in every run

In all nine auctions (13, 50, 100 and 400 participants, both database settings, plus a race to the
target with 400), every check passed:

- every bid the server confirmed was stored, nothing else was, and no bid was stored after the
  bidder was told it failed;
- bid numbers ran 1, 2, 3… with no gaps or repeats, and each raised the price by exactly 1 SAR;
- nobody bid twice in a row;
- no bid was accepted at or after the closing time (the last ones landed 4–18 ms before it);
- in the race to the target, exactly one bid reached it, it was the last, and the 300 after it
  were refused;
- the four winners were the top four by price, then by who got there first, with the right
  amount owed for each prize;
- every other participant got the entry fee back exactly once, and every wallet adds up;
- no live update was lost: 0 of 9.1 million deliveries missing, no dropped connections;
- **0 bids failed** because of the server: every refusal was a rule (auction over).

## What limits it

1. **One auction takes one bid at a time.** Each bid locks the auction's row, makes four or five
   trips to the database and commits — 7–10 ms here — before the next can start. So one auction
   accepts at most about 100–135 bids a second with the database next door, and every extra
   millisecond to the database lowers that. 400 people at 0.5 bids a second ask for 200 a second,
   and up to 800 in the last seconds, so their bids queue.
2. **A queued bid waits while holding a database connection.** At 400, all 100 connections were
   held by bids waiting for the same auction, and about 300 more requests were waiting for a
   connection — the leaderboard, snapshots, joins, other auctions, the store, and that auction's
   own closing. That is why the winners appeared 11–25 s late and the leaderboard fell 1–3 s
   behind, while the live price itself still reached every screen in tens of milliseconds.
3. **The busier it gets, the longer each bid holds the lock** (9 ms → 16 ms → 24 ms), as 400 live
   connections and hundreds of waiting requests compete for the server, so the ceiling falls just
   when it is needed most.

Not limits in these runs: price delivery (always fast, nothing lost), CPU (at most 4 cores here),
memory (under 600 MB). On a shared plan with a CPU or memory cap, those could become the next
limit at 400 — worth checking the plan's limits.

## Smaller findings

- **Prices can arrive swapped.** Each bid's update is sent from its own request, so two close
  bids can reach phones in either order. The app shows whichever arrived last, so it can briefly
  show the older price: 400 times for about 10 ms in the 400 run, and very often but for 3–4 ms in
  the target race. Every screen still ended on the right final price, even before the app's
  end-of-auction refresh.
- **Closing takes a moment.** "Auction finished" reached screens 0.2–1.6 s after the closing time,
  because the closing check runs every 2 seconds.
- **The first second after a restart is slower** (bids up to 360 ms) while .NET compiles the bid
  code; IIS restarts the app after it sits idle.

## Options (none applied — for decision)

1. **A bid queue per auction inside the server.** Bids for one auction wait their turn in memory
   instead of each holding a database connection while waiting for the lock. The database lock
   stays as the guarantee. This keeps connections free for everything else and lets the close
   run on time; bids that arrive after the closing time can be refused without touching the
   database. No new infrastructure, no Redis.
2. **Fewer database trips while holding the lock**, to raise the ceiling: read the participant
   before taking the lock, keep "who bid last" on the auction row instead of looking it up, and
   write the bid in one batch. Each trip saved matters more on SmarterASP, where a trip costs more.
3. **In the app, ignore a price update older than the one on screen** (bids carry their number).
4. Re-run these tests after each change against this baseline, then watch a live auction with
   `monitor`.

## Next on production

Deploy the diagnostics endpoint, then run `monitor` during the next live auction. Its database
command times and lock-hold times show how far SmarterASP's database really is, which sets the
delay to use here (`-DbDelayMs`) so local runs predict production.
