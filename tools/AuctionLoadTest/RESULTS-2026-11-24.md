# Winners announced before refunds, and a same-day check (24 Nov 2026)

Winners are now announced as soon as they are decided; refunds are paid afterwards and the
"your fee came back" message waits for them. 400 participants (`artifacts/loadtest/compare-v3-*.md`):

| Winners shown after the close | Baseline | Now |
|---|---|---|
| Database on this machine | 11.3 s | 0.7 s |
| Database 1 ms away | 25.4 s | 1.8 s |
| Race to the target | 22.3 s | 0.2 s |
| With a second auction alongside | 12.1 s | 0.4 s |

The machine's Docker database ran about twice as slow on 24 Nov as on 23 Nov (median command
1.9 ms against 0.8 ms, same code), so bid figures from different days are not comparable. The old
code (78be2c8) was rerun the same morning on the same machine (`compare-v3-sameday.md`):

| 400 participants, same day | Old code | New code |
|---|---|---|
| Bid wait p50 / p95 / p99 | 2.9 / 7.4 / 10.0 s | 2.7 / 4.2 / 4.4 s |
| Closing-burst bid wait p99 | 13.6 s | 4.5 s |
| Bids accepted per second | 75.8 | 85.1 |
| DB connections in use / waiting | 100 / 301 | 4 / 0 |
| Leaderboard lag p99 | 1.9 s | 0.3 s |
| Winners shown after the close | 10.4 s | 0.7 s |
| 400 joining at once, slowest | 8.8 s | 11.3 s |
| Memory peak | 491 MB | 605 MB |

Every closing check passed in every run; no bid failed and none was turned away as busy. At 400
the median bid still waits seconds: one auction still takes bids one at a time, and 400 people
asking for 200–800 a second is more than it can serve. Joins all at once are slower than before
because they now queue one by one (they no longer use up the connection pool doing it).
